# Подход к тестированию

## Цель

Поддерживать покрытие не ниже 80% и проверять самые важные сценарии приложения:

- бизнес-логика
- работа роутов
- авторизация
- фоновые задачи
- интеграции с внешними сервисами через моки

## Какие тесты используются

### Unit тесты

Проверяют отдельные функции и классы без реальной базы данных, RabbitMQ и внешних HTTP-запросов.

Примеры:

- `core.auth`
- `utils.*`
- `services.exchange_client.crud`
- `services.queue_producer`
- `services.queue_consumer`

### Integration тесты

Проверяют работу API-роутов через `TestClient`, но внешние зависимости подменяются моками.

Примеры:

- логин и получение текущего пользователя
- чтение и создание товаров
- запуск фоновых задач
- вызовы роутов внешних сервисов

## Что именно важно тестировать

### Пользователи

- успешная регистрация
- успешный логин
- ошибка при неверных данных
- получение текущего пользователя по токену

### Товары

- чтение своих товаров
- создание товара
- обновление товара
- удаление товара
- обработка ошибок в CRUD-слое

### Очереди и background tasks

- успешная отправка задачи в очередь
- повторы при ошибках в consumer
- перевод задачи в error queue после превышения лимита попыток
- запуск фоновых задач через API

### Внешние интеграции

- успешный ответ внешнего API
- таймауты и ошибки сети
- корректная обработка недоступных данных

## Команды

Запуск всех тестов:

```bash
poetry run pytest
```

Запуск с покрытием:

```bash
poetry run coverage run -m pytest
poetry run coverage report -m
```

## Организация тестов

- `tests/test_*.py` — отдельные сценарии по модулям
- unit тесты должны быть быстрыми и изолированными
- integration тесты должны проверять поведение API, а не внутреннюю реализацию

## Практические правила

- для HTTP используем моки вместо реальных сетевых вызовов
- для RabbitMQ используем `MagicMock` и `AsyncMock`
- для ошибок проверяем не только статус, но и текст ответа
- новые тесты добавляем рядом с близкой по смыслу функциональностью

## Что считается хорошим тестом

Хороший тест:

- проверяет одно понятное поведение
- не зависит от внешней среды
- быстро выполняется
- падает только по реальной проблеме в коде
