# План инфраструктуры

## Текущая схема

Сейчас проект состоит из таких частей:

1. FastAPI-приложение
2. PostgreSQL для хранения пользователей и товаров
3. RabbitMQ для очередей задач
4. Alembic для миграций базы

## Поток данных

### Основной API

- клиент отправляет запрос в FastAPI
- FastAPI обращается к базе данных через SQLAlchemy Async
- при необходимости приложение отправляет задачу в RabbitMQ

### Асинхронная обработка

- producer публикует задачу в очередь `processing`
- consumer читает сообщения из очереди
- при ошибке задача повторяется несколько раз
- если лимит попыток исчерпан, сообщение уходит в `processing_errors`

## Порты

По `docker-compose.yml` используются:

- PostgreSQL: `5433 -> 5432`
- RabbitMQ AMQP: `5673 -> 5672`
- RabbitMQ Management UI: `15673 -> 15672`

## Переменные окружения

Для инфраструктуры обязательны:

- `DB_URL`
- `RABBITMQ_HOST`
- `RABBITMQ_PORT`
- `RABBITMQ_USER`
- `RABBITMQ_PASSWORD`

Для безопасности приложения обязательны:

- `SECRET_KEY`
- `ALGORITHM`
- `ACCESS_TOKEN_EXPIRE_MINUTES`

## Минимальный план эксплуатации

### Логи

- логи приложения пишутся в `app.log`
- логи стоит собирать централизованно, если проект будет расти

### Мониторинг

На текущем этапе достаточно:

- следить за доступностью API
- контролировать подключение к PostgreSQL
- смотреть состояние очередей RabbitMQ
- отслеживать количество ошибок в `processing_errors`

### Резервирование

- база данных должна иметь backup
- для RabbitMQ желательно понимать, какие очереди критичны для восстановления

## Текущие ограничения

- нет отдельного production-конфига
- нет healthcheck endpoint для оркестратора
- нет централизованного мониторинга и алертов
- внешние интеграции пока не имеют отдельного слоя retry/metrics
